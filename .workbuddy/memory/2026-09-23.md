# 2026-09-23

## 亚马逊价格抓取：从逐条请求改为 Firecrawl 批量任务（提速 + 消除超时）

**背景**：用户反馈批量获取亚马逊价格太慢，且频繁出现 `timeout of 90000ms exceeded`。
原流程是前端 2 个 worker 逐条 POST `/product-prices/amazon/:id/fetch`，每条一次 Firecrawl
`/v2/scrape`，后端还有并发闸门（容量 2）+ 重试退避，整条链路靠一个长连接 HTTP 请求撑着。

**关键实测数据（真实 key）**：
- 单个 `/v2/scrape` 亚马逊页面约 7~8s；页面 HTML 约 0.8~1.8MB（只有 `html` 字段，`rawHtml` 为空）。
- `/v2/batch/scrape`：提交约 1s，3 个 URL 约 11~27s 完成，服务端并发执行。
- 批量返回结构：`{success,status,completed,total,creditsUsed,data:[{metadata:{sourceURL,url,statusCode,error}, html}]}`。
  **必须用 `metadata.sourceURL` 取 ASIN**，`metadata.url` 是重定向后的地址（带 `?lv=shuf&channelId=...`）。

**改动**：
- 新增 `backend/internal/handler/product_price_batch.go`：
  - `submitAmazonBatchScrape` → POST `/v2/batch/scrape`（`maxConcurrency=5`、`ignoreInvalidURLs`）；
    401/402 终态，429/5xx/网络错误可重试（**任务没被接受就不扣额度，可安全重试**）；
  - `fetchAmazonBatchStatus` → GET `/v2/batch/scrape/{id}` 轮询；一旦任务被接受就**只轮询不再重提**，
    重提会把整批页面重新计费；
  - `scrapeAmazonChunk` 每批 20 个 ASIN，轮询间隔 3s，单批预算 10min；
  - 异步任务 + 进度查询：`StartAmazonPriceBatchFetch` / `GetAmazonPriceBatchFetch` /
    `CancelAmazonPriceBatchFetch`，同一时间只允许一个运行中的任务（第二个返回 409）。
- 路由（**重要**：gin 不允许在已有 `:id` 通配的同一层再注册静态段，会 panic）：
  因此用独立前缀 `POST /product-prices/fetch-batch`、`GET /product-prices/fetch-batch/:jobId`、
  `POST /product-prices/fetch-batch/:jobId/cancel`，而不是 `/product-prices/amazon/...`。
- `web/src/views/ProductPricesView.vue`：去掉 2-worker 逐条请求，改为「提交任务 → 每 1.5s 轮询进度」，
  所有请求都是短请求；新增 `fetchJobId`、`stopAmazonPriceFetch()`（停止按钮改为真正调用 cancel）。
- 新增 `product_price_batch_test.go`（4 个用例：ASIN 提取、429 后重试提交、401 不重试、上游失败透传）。

## 修复「Firecrawl 批量任务未返回该商品页面」

**排查过程（实测，别猜）**：
1. 塞一个不存在的 ASIN（B000000000）进批量任务 → Firecrawl **照样返回条目**（亚马逊"找不到该页"页，428KB）。
   所以这个报错**不是** ASIN 无效导致的。
2. 提交 20 个 URL（约 10MB+）→ 状态接口返回 `data` 20 条、`next` 为空。**没触发 10MB 分页**。
   （20 个 URL 里有重复 ASIN，去重后 13 个，全部命中。）

**真正会吞掉原因的两处**（已修）：
- 任务状态是 `failed`/`cancelled` 且 `data` 为空时，原来只返回空 map，整批商品都被报成
  "未返回该商品页面"，上游原因被丢弃 → 新增 `amazonBatchJobFailure()` 透传 status + error。
- 任务 `completed` 但个别页面缺失 → 新增 `missingAmazonBatchASINs()`，对缺失的 ASIN
  **单独再提交一个小批量补抓一次**（去重后再补），仍缺才逐条报错。
- 报错文案带上 ASIN：`Firecrawl 未返回该商品页面（ASIN xxx），请稍后重试`。

**顺带保留了 10MB 分页**：文档明说 `next` = "URL to retrieve the next 10MB of data"，
虽然实测没触发，仍按 `next` 递归翻页（上限 100 页）以防大批量时截断。
配套新增 3 个用例：翻页合并、缺失补抓、失败透传原因。

**锁约定（别改顺序）**：`amazonPriceBatchMu` → `job.mu`，三处（启动、prune、run 收尾）必须一致；
`job.cancel` 的写和读都要在 `job.mu` 下。已补 `TestAmazonBatchJobCancelStopsRemainingChunks`
（取消后剩余批次不再处理 + 并发轮询快照），跑 `-count=5` 无抖动。
本机 Go 无 cgo，`go test -race` 不可用（报 `-race requires cgo`）。

**关于 90000ms**：全仓库（含 git 历史）都没有 90000 这个值，前端 axios 只配了 3000000 与 170000。
改成异步任务后不再存在长连接请求，该报错路径已被消除；单次解析/保存逻辑不变。

**待确认**：`maxAge` 仍是 0（每次都实时抓取，不读 Firecrawl 缓存）。若用户对价格时效要求放宽到
几小时，可以把 `maxAge` 调大，官方称可提速数倍。

## 回退：去掉 Firecrawl 批量接口，改回并发单条抓取（用户明确要求不要批量）

**症状**：261 个商品一直显示 0/261，Firecrawl 后台只有一条调用记录；报错
「读取 Firecrawl 批量任务结果失败，请重试」。

**实测根因**（真实 key，20 个 URL 一批）：
- 单批 20 页要 **222s** 才 completed（≈11s/页）。261 个 = 14 批串行 ≈ **52 分钟**。
- 状态轮询请求本身会被 Firecrawl 挂起 **80~120s**（第 3、4 次轮询各耗 79.7s / 120.4s），
  接近 client.Timeout（180s）→ 一旦超时就解码失败，报「读取…结果失败」。
- 终态时 `completed=20/20` 但 `data` 只有 9 条，`next` 非空 → 10MB 分页确实生效，要翻页才拿得全。
- 进度只在**整批完成后**才 +20，所以用户在第一批跑完前永远看到 0/261，且 Firecrawl 后台只有 1 条提交记录。

**新实现**（`product_price_batch.go` 重写，保留 job 框架/路由/前端契约不变）：
- 删除 batch scrape 全部代码（submit / status / 分页 / 补抓 / `firecrawlBatchDocument` 等）。
- **按 ASIN 分组去重**：`groupAmazonPriceBatchItems()` —— 多个 SKU 共用一个 ASIN 时只抓一次页面；
  ASIN 无效的商品直接判失败，不消耗额度。
- worker pool：`amazonPriceBatchWorkers = amazonPriceScrapeParallel`（=2，与全局抓取闸门一致，
  避免双重排队）；每个 worker 调用现成的 `fetchAmazonPrice`（已含 429 退避重试、无货识别）。
- **每抓完一个 ASIN 立即更新 Done/Scraped**，进度实时增长；job 新增 `asins` / `scraped` 字段。
- client.Timeout 改为 `amazonPriceAttemptTimeout`（70s），单次尝试超时即重试，不让 worker 卡几分钟。

**实测对比**：并发单条 **3.3s/ASIN**（4 个 ASIN / 2 worker = 13.2s），比批量的 11s/页快约 3 倍。
261 个商品预计 10~15 分钟（去重后更少）。

**新增测试**（5 个，替换原批量测试）：ASIN 分组去重 + 无效 ASIN 前置失败、每个 ASIN 只抓一次
（3 SKU / 2 ASIN → 2 次请求、3 条结果）、进度边跑边报、并发不超过 `amazonPriceBatchWorkers`、
取消后剩余页面不再处理且已处理的都有结果。

**前端**：进度文案在去重数 ≠ 商品数时补一句「已抓 N/M 个商品页」，避免 261 个商品只抓 180 次
让人以为漏了。其余（1.5s 轮询、取消按钮）不变。

**可调项**：套餐并发更高时，把 `amazonPriceScrapeParallel`（`product_price_fetch.go`）
调大即可同时提升单条抓取和批量任务的并发度。

## 修复「单位价被当成折扣价」（B08CSBQ9G2）

**现象**：页面显示 `$26.99` 和 `$13.63 per count`，程序输出 原价 26.99 / 折扣价 13.63。

**根因**（抓真实页面 dump DOM 确认）：单位价节点的 class 是
`a-price a-text-price apex-priceperunit-value`（**同时带 a-price 和 a-text-price**），
真正的售价是 `a-price aok-align-center apex-pricetopay-value`（只有 a-price）。
于是 13.63 被判成 `a-text-price` 进 **lists（原价集合）**，26.99 进 currents；
`amazonPriceResult` 发现 list(13.63) < current(26.99) 就 swap，把单位价输出成折扣价。
旁边还有 `span.aok-offscreen apex-priceperunit-accessibility-label` 写着 "$13.63 per count"
（注意是 `aok-offscreen`，不匹配 `a-offscreen`，所以不会被收集）。

**修复**（`product_price_html.go`）：新增 `amazonIsUnitPriceNode(n, stop, attr)`，
沿祖先链（上到 region 为止）检查 class+id 小写后是否含 `priceperunit` / `perunit`；
在**两处**收集 `a-offscreen` 的循环里跳过单位价——主价格区扫描 `regionPrices` 和
清洗 HTML 的兜底扫描（同一 bug 的两条路径，都要修）。只排节点，不排整个 region，
否则会把正确的 26.99 一起丢掉。

**新增测试**：`TestAmazonHTMLPriceIgnoresUnitPrice`（单位价不得变成折扣价）、
`TestAmazonHTMLPriceKeepsRealDiscountBesideUnitPrice`（排除单位价后真实折扣仍要保留，
防止误伤——fixture 里同时放 basisprice $26.99 / pricetopay $19.99 / priceperunit $9.99，
期望 26.99 / 19.99）。

**真实回归**：B08CSBQ9G2 → 26.99 无折扣；B0DWK6K6L5 → 55.99/49.78；B0G7H6Q7BZ → 66.99；
B0B4G46RC3 → 无货。handler 包全量测试通过。

## 价格模型改为三档：Regular Price / Prime Member / Best Deal（用户主动纠正抓取语义）

**用户原话要点**：
- 有 `Regular Price` 与 `Prime Member` 两个区块 → 抓这两个区块底下的价格；
- 价格上方带 `Limited time deal`（秒杀）→ 秒杀价 = `Buy New` 底下的价格；
- 三者都没有（如 B08CSBQ9G2）→ **保持原抓取逻辑不变**；
- **不要抓 List Price 后面的价格**；
- 表格列名：原价→Regular Price，折扣价→Prime Member，再加一列 Best Deal。

**用户确认的两个填空规则**（AskUserQuestion）：
- 秒杀商品 Regular Price **留空**（不要 List Price），只填 Best Deal；
- 有 Regular/Prime 但无秒杀时 Best Deal **留空**。

**真实 DOM 结构**（抓 6 个页面 dump 得到，关键结论）：
- caption 用 **feature_div id** 定位：`div#newAccordionCaption_feature_div` 文本是
  `Regular Price` 或 `Buy New`；`div#primeSavingsUpsellCaption_feature_div` 文本是
  `Prime Member Price`。
- 秒杀判定：**`div#dealBadge_feature_div` 的文本含 "Limited time deal"**，且祖先 id 含
  `newaccordionrow`（该 badge 在 usedAccordionRow 下也存在，但是空的，必须排除）。
- 真实现价 = `apex-pricetopay-value`（如 49.78 / 53.98 / 75.99）。
- **List Price 就是 `apex-basisprice-value`**（B0DWK6K6L5 的 $55.99、B07X395JXY 的 $69.99）
  —— 之前正是把它当成"原价"，用户说的不要抓的就是它。
- 单位价 = `apex-priceperunit-value`（仍要排除）。
- **`?th=1` 不影响**：带与不带 th=1 抓下来的区块与价格完全一致，抓取 URL 保持
  `https://www.amazon.com/dp/{ASIN}` 不变。

**实现**（`product_price_html.go`）：
- 新增 `amazonAccordionOffers(root, attr, content)`：先给所有节点编 DOM 序号，收集
  所有 `a-offscreen` 价格（排除 derived），再按 caption 找"该 caption 之后、最近祖先内的
  第一个价格"（`priceAfter`，祖先最多上溯 8 层）。命中即优先返回，未命中才走原有逻辑。
- `amazonIsUnitPriceNode` → 改名 `amazonIsDerivedPriceNode`，排除项加上 **basisprice**
  （List Price）。两处调用点（主区域扫描 + 清洗 HTML 兜底扫描）同步。
- 组装：`regular != nil || prime != nil` → {Price: regular, SalePrice: prime, BestDeal: deal?}；
  仅 `deal && buyNew != nil` → **只填 BestDeal，Price/SalePrice 留 nil**；都不命中 → 回退原逻辑。

**数据层**：
- 迁移 `backend/migrations/000069_add_amazon_best_deal.{up,down}.sql`（`numeric(10,2)`）。
- `model.ProductSKU` / `productPriceRow` 加 `AmazonBestDeal`；`productPriceInput` 加 `BestDeal`。
- 三处 Select 列表 + `saveFetchedAmazonPrice`（Updates 与乐观锁 WHERE）都加上该列；
  `UpdateProductPrice` 也保存三列。
- 语义映射：`amazon_price`=Regular Price，`amazon_sale_price`=Prime Member，新列=Best Deal。

**前端** `ProductPricesView.vue`：表头 Amazon colspan 3→4、colgroup/骨架屏同步 8→9 列，
新增 Best Deal 单元格；编辑表单新增 Best Deal 输入（`dealInput` ref、`edit(item,'amazon','deal')`）；
`previewPrice` 改为取三档中的**最低价**；校验文案同步改名。

**真实验证**（`fetchAmazonPrice` 完整链路）：
B0CJFG5W4B → 75.99 / 71.99 / 空；B07X395JXY → 空 / 空 / 53.98；
B08CSBQ9G2 → 26.99 / 空 / 空；B0DWK6K6L5 → 空 / 空 / 49.78。

**注意**：旧逻辑已写入库的历史价格（如 B0DWK6K6L5 的 amazon_price=55.99 其实是 List Price）
需要**重抓一次**才会被纠正。

**筛选器回归修复**（`product_price.go`，三档改造的副作用）：
- `filter=missing`（待补全）原为 `amazon_price IS NULL OR ...`，秒杀商品 amazon_price 为 NULL
  会被误判成待补全 → 改为**三档全 NULL** 才算。
- `filter=sale`（有折扣）原为 `amazon_sale_price IS NOT NULL`，只有 Best Deal 的秒杀商品会漏掉
  → 改为 `amazon_sale_price IS NOT NULL OR amazon_best_deal IS NOT NULL`。
前端筛选标签未改名（"有折扣"≈有会员价或秒杀价）。
